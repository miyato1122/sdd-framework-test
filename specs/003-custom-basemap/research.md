# 研究メモ（Phase 0）: ユーザー定義のオリジナル背景地図の追加

本フィーチャーは **002（背景地図スイッチャー）への増分拡張**。002 の確定事項（`research.md` R1〜R7／`basemaps.js` レジストリ＋ `OpacityControl` 転用＋既定 `AttributionControl` 追従＋ `map.on('error')`）を出発点に、003 で新たに生じる設計不明点のみを解消する。spec に `[NEEDS CLARIFICATION]` は無く、Clarifications（2026-05-18・Q1〜Q4）で要件は確定済み。出典規約・実コードを実機/実ファイルで確認した。

> 検証前提（憲章 II・過去知見）: `node_modules` 未配置のため本 Phase ではビルド/テストを実行していない。プラグイン描画 DOM 依存・UI/アクセシビリティ挙動は静的解析だけで断定せず、`quickstart.md` の手動スモークで実機確認する（描画/コントロール経路は手動スモーク＝憲章 II）。`npm run build`/`npm run test` の成功主張はクリーンインストール環境での再検証を必須とする。

## R1′. スイッチャー末尾の「追加ボタン」と実行時の動的追加（002 R1 の意図的見直し）

- **Decision**: 背景地図スイッチャー（bottom-left）を、**プラグインの描画 DOM 形状（`#opacity-control` コンテナ＋ネイティブ `input[type=radio]`＋`label[for]`）を踏襲した小さな自作 MapLibre `IControl`** に置き換える。この自作コントロールが「レジストリからのラジオ描画」「排他選択＝可視レイヤー切替」「一覧末尾の『＋ 背景地図を追加』ボタン」「追加フォームの開閉」を担う。ハザード（top-left）・skhb（top-right）の `OpacityControl` 2 インスタンスは**一切変更しない**。
- **Rationale**:
  - `maplibre-gl-opacity@^1.8.0` の `OpacityControl` は**構築時に渡した `baseLayers` 静的マップ**からラジオを描画する設計で、002 は構築後に `baseLayers` を変更していない（`main.js`）。「一覧末尾に非レイヤーの追加ボタンを足す」「実行時にレジストリを増やしてラジオを増設する」公開 API は存在しない。`node_modules` 未配置で内部実装の静的検証も不可。
  - 002 R1 は自作コントロールを「コード量・a11y・スタイル二重化」を理由に却下したが、それは**動的追加・末尾アフォーダンスが要件に無かった前提**での判断。003 の FR-001（末尾の追加操作）／FR-004（実行時追加）／FR-007（追加分の現在選択表示）／FR-011（既存挙動の回帰禁止）により前提が変わったため、設計判断を意図的に見直す（増分拡張で過去判断を再評価した記録）。
  - 自作コントロールでも**スタイル二重化は発生しない**: 既存 `opacity-control.css` は `#opacity-control` セレクタ（複数インスタンスに適用済みの既知運用）＋ `.maplibregl-ctrl-bottom-left #opacity-control { width:auto; white-space:nowrap }`／`label{cursor:pointer}` で構成される。自作コントロールを同一 DOM 形状（`#opacity-control` 配下のラジオ＋`label[for]`）で描画すれば**既存共有 CSS がそのまま適用**され、見た目・操作感は 002 と同一に保てる（憲章 III：共有スタイル再利用・一貫アフォーダンス・インライン禁止）。
  - a11y はネイティブ `radio`＋`label[for]` でキーボード到達・ラベルクリックを満たす（憲章 III：新規 UI は既存 a11y を後退させない）。ただし `label[for]` とキーボード挙動は**実機確認が必要**（過去知見: 002 で `label[for]` 根拠の断定が実機 NG だった）→ quickstart スモークで必須確認。
- **Alternatives considered**:
  - **A: `OpacityControl` を維持し、描画後の DOM に追加ボタンを差し込み＋追加時にコントロールを作り直す**（古い背景 `OpacityControl` を `removeControl`→新 `baseLayers` で再生成、現在選択を再適用）。新規依存ゼロは満たすが、(1) プラグイン描画 DOM への注入が公開 API 外で静的検証不可・脆弱（過去知見の「静的解析で断定しない」に抵触）、(2) 再生成時の現在選択保全ロジックが複雑、(3) 他 2 インスタンスへ副作用を出さない保証が難しい。FR-011 の回帰リスクが上がるため却下。
  - **B: 新規 UI プラグインを導入**（例: maplibre-gl-legend 等）→ 新規依存。利用者制約・憲章 I（新規依存より既存優先）違反。却下。
  - **C: 何も足さず別パネルで追加**（スイッチャー外に独立フォーム）→ FR-001「一覧最後尾に追加ボタン」を満たさず spec の利用イメージから乖離。却下。

## R2. ユーザー定義ラスタソースのシステム既定ズーム範囲（Clarifications Q1）

- **Decision**: ユーザー定義背景の MapLibre raster ソースは **`tileSize:256`／`minzoom` 未指定（=0 相当）／`maxzoom:19`** を既定とする。利用者は方式・ズーム範囲を入力しない（XYZ 固定）。
- **Rationale**: アプリは `minZoom:5 / maxZoom:18`（`main.js`）。ソース `maxzoom` を 19 にすれば全操作ズーム域をカバーし、提供元が低ズームしか持たない場合でも MapLibre が**オーバーズーム描画**するため最大ズームで破綻しない（002 R2 の白地図 z14 と同じ堅牢化方針）。`minzoom` を絞らないことで低ズームのタイル欠落を避ける。これは「方式・ズーム範囲を入力させない（システム既定）」という Q1 決定の最小実装で、入力負荷・検証・テストを増やさない。
- **Alternatives considered**: 利用者にズーム範囲を入力させる → Q1 でスコープ外と確定。却下。`maxzoom` を 18（地図 maxZoom と同値）→ 19 にしても害はなく将来の maxZoom 引き上げに頑健なため 19 採用。

## R3. タイル取得元 URL／表示名の検証契約（Clarifications Q2・Q3、FR-008）

- **Decision**: 検証は **`basemaps.js` の純粋関数**として実装し決定論的にユニットテスト（憲章 II）。判定規則:
  1. 必須項目（表示名・タイル取得元・出典）が非空（前後空白を除去後）。
  2. タイル取得元が **URL として解釈可能**（`new URL()` で例外を投げない）。
  3. タイル座標の差し込み箇所 **`{z}` `{x}` `{y}` を全て含む**。
  4. URL スキームが **`http:` または `https:` のみ**（`javascript:`・`data:` 等は不正）。
  5. 表示名が**既存の全背景地図（組み込み4種＋追加済みユーザー定義）と重複しない**（前後空白除去・完全一致比較）。
  - いずれか不成立なら追加せず、**不成立の理由を項目単位で**返す（無言失敗禁止＝FR-008）。混在コンテンツ（`https` ページ上の `http` タイル）はスキーム上は許可し、結果生じる取得失敗は FR-010（`map.on('error')` トースト）の扱いに委ねる。
- **Rationale**: Q2/Q3 の確定事項をそのまま機械的判定に落とすことで FR-008・SC-004（無言成功 0%）をテスト可能・境界明確化。`URL` は標準 API（新規依存なし・憲章 I）。純粋関数化で実ネットワーク非依存の決定論テスト（憲章 II）。
- **Alternatives considered**: 追加時に実タイルを取得して到達性確認（spec Q2 の選択肢 C） → Q2 で却下済み（遅延・誤判定）。正規表現のみで URL 構文を自前判定 → `URL` 標準 API の方が堅牢で却下。

## R4. ユーザー定義背景の動的追加と出典自動切替・現在選択（FR-004/005/006/007、002 R3 再利用）

- **Decision**: 追加確定時、`basemaps.js` の純粋関数が入力から **BaseMap 形状オブジェクト**（`id` を実行時生成、`sourceId`、`source`＝R2 既定＋利用者入力 `attribution`、`isDefault:false`、`isUserDefined:true`）を生成。`main.js` 側は 002 と同じ手順で `map.addSource(sourceId, source)`／`map.addLayer({id:'<id>-layer', type:'raster', layout:{visibility:'none'}}, 'hazard_flood-layer')`（osm-layer の直後・ハザード背面に挿入）し、自作コントロールのラジオ一覧に当該エントリを追記する。出典は **002 R3 の既定 `AttributionControl` 自動集約をそのまま利用**（可視ソースの `attribution` のみ集約）。追加直後は**選択を変更しない**（Clarifications Q4：自動選択しない＝現在の可視レイヤー・現在選択を不変に保つ）。
- **Rationale**: ソース/レイヤー追加・出典自動追従は 002 で確立した手順を踏襲（増分拡張＝新規アーキ要素なし）。利用者入力 `attribution` をソース定義に入れるだけで、選択時に既定 AttributionControl が自動表示し、組み込みへ戻すと自動で戻る（FR-006、追加の命令的コードほぼ不要）。Q4 により追加と選択を分離し、追加→明示選択で初めて可視切替（FR-004 後段）。
- **Alternatives considered**: 追加時に自動選択して即表示（spec Q4 選択肢 A） → Q4 で却下済み。出典 DOM を自前差し替え → 002 R3 で却下済み（既定挙動で足りる）。

## R5. 追加フォームの UI 形態とエラー/状態表示（FR-002/008/009/012、憲章 III）

- **Decision**: 追加フォームは**自作コントロール内に展開するインラインパネル**（モーダルではない）として実装。表示名・タイル取得元（URL テンプレート）・出典の入力欄、確定・キャンセル（FR-009）、検証 NG 時の項目別エラー表示（FR-008）を持つ。スタイルは共有 `style.css` に専用クラスを追加（インライン禁止＝憲章 III）。フォーム表示中も地図のズーム/パンは継続可能（FR-012：全画面ブロック・フリーズ禁止）。タイル取得失敗は **002 の既存 `.map-error-toast`＋`map.on('error')` を再利用**（FR-010）。
- **Rationale**: 憲章 III「全画面ブロック禁止／読み込み中・空・エラー状態の視覚処理／レイアウトシフト抑制」。インラインパネルはモーダルより地図操作を妨げず、bottom-left の確立配置（他コントロールと非衝突＝002 R6）の延長で収まる。エラー通知は既存資産再利用で二重実装回避（憲章 I）。
- **Alternatives considered**: 全画面モーダル → 憲章 III「全画面ブロック禁止」に抵触。却下。`window.prompt` 連続入力 → 検証フィードバック・a11y・一貫アフォーダンスに劣る（憲章 III）。却下。

## R6. テスト戦略（憲章 II）

- **Decision**: `basemaps.js` の新規純粋ロジック（入力検証・BaseMap 生成・既定ズーム定数・一意性判定）を `tests/unit/basemaps.test.mjs` に追記し `node --test` で決定論的に検証（実ネットワーク非依存）。自作コントロール／フォーム描画・選択切替・出典自動追従・キーボード/`label[for]` a11y・FR-011 回帰（組み込み4種選択・既定 OSM・出典自動表示が不変）は **`quickstart.md` の手動スモーク**で確認。`npm run build` 成功を必須ゲートとし、クリーンインストール環境で再検証する（過去知見: lockfile 再現環境での偽green を回避）。
- **Rationale**: 憲章 II「純粋ロジックは決定論的ユニットテスト」「描画経路は手動スモーク文書化」。003 で純粋部はすべて `basemaps.js` に閉じるためテスト戦略は 002 と一貫。
- **Alternatives considered**: ブラウザ E2E 自動化 → 新規依存・スコープ過大（利用者制約／002 R7 と同じ理由）。却下。

## R7. 出典入力のセキュリティ（生 HTML 非受理・ラベル/URL 分離。Clarifications Q5・実装フィードバック）

- **Decision**: 出典は単一の生文字列ではなく **「出典の表示名（必須・プレーンテキスト）」＋「出典リンク URL（任意・`http(s)`）」** に分離して入力させる。`basemaps.js` の純粋関数 `escapeHtml()`／`buildAttributionHtml(label, url)` が、表示名を HTML エスケープし、URL があれば検証済み（`validateCustomBasemapInput` 規則8）として `<a href target=_blank rel="noopener noreferrer">` を構築、無ければエスケープ済みテキストのみを返す。利用者の生 HTML は `source.attribution` に一切流さない。
- **Rationale**: MapLibre の `AttributionControl` は出典を **`innerHTML` で描画**するため、生文字列をそのまま渡す当初設計は `<script>`/`<img onerror>` 等の HTML/スクリプトインジェクション経路だった（セッション内・自分入力中心でも排除すべき自己 XSS）。ラベル/URL 分離＋エスケープ＋スキーム検証で、入力がどうであれ出力にタグが現れない／危険スキームのリンクが生成されないことを**構造的に保証**でき、純粋関数として決定論ユニットテスト可能（憲章 II）。標準 `URL`／文字列置換のみで**新規依存ゼロ**（憲章 I）。組み込み4種の出典は内部定数（利用者入力ではない）ため影響なし＝FR-011 非回帰。
- **Alternatives considered**:
  - 生 HTML を受理し DOMPurify 等でサニタイズ → 新規依存（利用者制約・憲章 I 違反）。却下。
  - 生 HTML をそのまま `attribution` へ（当初実装） → `innerHTML` 描画への XSS 経路。却下（本 R7 で是正）。
  - 出典をテキストのみ（リンク不可） → 提供元規約はリンク付き表記を求めることが多く UX/コンプライアンス上不足。リンクは「URL を分離入力＋システム構築」で安全に提供。却下。

---

**結論**: spec に未解決クラリフィケーションは無く、本研究で 003 固有の設計不明点（末尾追加 UI／動的追加方式／既定ズーム／検証契約／フォーム形態／出典のセキュア入力）を全て解消。**新規依存ゼロ・新規アーキ要素ゼロ**で FR-001〜012・SC-001〜006 を満たす設計が確定。002 からの主要差分は「背景スイッチャーのみ自作 IControl へ置換（ハザード/skhb は不変・behavior 非回帰）」および「出典は生 HTML 非受理＝ラベル/URL 分離＋システム構築（R7・Q5）」であり、いずれも憲章違反ではなく設計判断の記録（R1′ は 002 R1 見直し、R7 は実装フィードバックによるセキュリティ強化）。Phase 1 へ進行可。
